# Bezirk → Abschnitt → Feuerwehr-Hierarchie + Drohnengruppen-Aufteilung Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Expand app-177 from one Abschnitt (AFKDO Purkersdorf, 9 Feuerwehren, one flat Drohnengruppe) to
the full Bezirk 17 St. Pölten (7 Abschnitte, 124 real Feuerwehren/BTF, 4 named Drohnengruppen with
mandatory single-group membership), with a new Bezirksadmin role above the now-per-Abschnitt-scoped
existing admin role.

**Architecture:** Additive schema first (new tables/columns, all nullable), then a data-backfill migration
that gives every existing row a value under the new model, then application-code changes (session/
permissions, then call sites, then event-visibility fixes, then drone-module scoping, then admin-UI
polish). This ordering means the app keeps working correctly after every single task — nothing is left in
a broken intermediate state between tasks.

**Tech Stack:** Next.js App Router (Server Components/Actions), Prisma/PostgreSQL, TypeScript, Tailwind,
shadcn/ui `Select`. No test framework exists in this repo — verification is via `npx tsc --noEmit`,
`npm run build`, and standalone Node scripts run with `npx tsx` against the real dev database (the
established verification pattern for every feature in this codebase; see any "Verified directly" note in
CLAUDE.md for examples of the same style).

## Global Constraints

- No test suite exists — every task's verification step is `tsc`/`build` plus a standalone `tsx` script
  or direct DB check, never a fabricated test file.
- Never hand-edit an already-committed migration file. New migrations only.
- Migrations follow the existing "nullable → backfill → `NOT NULL`" sequence already used for
  `Organization.nummer` (see `prisma/migrations/20260810090000_organization_nummer/`) wherever a column is
  being tightened on a table with existing rows.
- All new/changed user-facing copy is German, matching the existing convention.
- `prisma/data/feuerwehren-bezirk-17-raw.json` (already committed) is the only source of truth for the 124
  Feuerwehr rows — never hand-type Feuerwehr names/numbers into a task.
- `isSiteAdmin` is retired in this plan and must not reappear in any new code written by any task —
  `isBezirksAdmin` / `canManageAbschnittFor` / the enriched `feuerwehrAdminOrgIds` replace it everywhere.
- Full design rationale for every decision below lives in
  `docs/superpowers/specs/2026-08-09-bezirk-abschnitt-drohnengruppen-design.md` — read it once before
  starting Task 1, it explains *why*, this plan only tells you *what* and *exactly how*.

### Task 2: Data backfill migration (District/AFKDO-Purkersdorf-Gruppe, droneGroupId verpflichtend)

**Note:** this task deliberately does **not** touch `AppSettings.droneFlightNotificationEmail`/
`droneQuickRegisterToken` yet, even though the design spec eventually removes both — those columns stay in
place, unused-but-harmless, until Task 9, which fixes every remaining reader of them (`src/lib/settings.ts`
and its callers) and drops the columns in the same task. Removing them here would leave `tsc`/`npm run
build` broken for the whole repo across Tasks 3–8, which is exactly the kind of "broken intermediate state
between tasks" this plan's Architecture section says to avoid.

**Files:**
- Create: `prisma/migrations/<timestamp>_hierarchie_backfill/migration.sql` (hand-written, following the
  `20260810090000_organization_nummer` precedent of combining backfill + `NOT NULL` in one file)
- Modify: `prisma/schema.prisma` (tighten `droneGroupId` to `NOT NULL` on 3 models only — `AppSettings` is
  untouched in this task)

**Interfaces:**
- Consumes: `District`, `DroneGroup`, `Organization.districtId`/`parentId` from Task 1.
- Produces: exactly one `District` row (`number: '17'`), the existing Purkersdorf `Organization` row has
  `districtId` set, exactly one `DroneGroup` row named `'AFKDO Purkersdorf'` anchored to that
  organization, every pre-existing `DrohnengruppeMembership`/`DroneDocument`/`Drone` row has
  `droneGroupId` set to that group's id and the column is now `NOT NULL`.

- [ ] **Step 1: Tighten the schema first (so `prisma migrate dev` generates the right diff)**

In `prisma/schema.prisma`, change `droneGroupId String?` to `droneGroupId String` (drop the `?`) on
`DrohnengruppeMembership`, `DroneDocument`, and `Drone` (all three — **not** `Event`, which stays nullable
forever). Also change their relation field from `DroneGroup?` to `DroneGroup` (drop the `?`). Do **not**
touch `model AppSettings` in this task (see the note above).

- [ ] **Step 2: Create the migration directory and write the hand-authored SQL**

```bash
npx prisma migrate dev --name hierarchie_backfill --create-only
```

This generates an empty-ish migration folder with a `migration.sql` file containing Prisma's
auto-generated `ALTER TABLE ... ALTER COLUMN ... SET NOT NULL` statements for the three tightened columns.
**Do not run it yet.** Open the generated file and add the backfill statements described in Step 3
**before** every `SET NOT NULL` statement in the file (a `NOT NULL` constraint fails immediately if any
existing row is still `NULL`, so the backfill must run first within the same transaction).

- [ ] **Step 3: Insert these backfill statements at the top of the generated `migration.sql`, before anything else**

```sql
-- Bezirk 17 St. Pölten (bislang kein Bezirk modelliert - die App kannte nur einen Abschnitt).
INSERT INTO "District" (id, number, name)
VALUES ('district-17', '17', 'St. Pölten');

-- Der bestehende einzige Abschnitt (AFKDO Purkersdorf) gehört zu diesem Bezirk.
UPDATE "Organization"
SET "districtId" = 'district-17'
WHERE name = 'Abschnittsfeuerwehrkommando Purkersdorf';

-- Die bisherige einzige (flache) Drohnengruppe wird zur benannten Gruppe "AFKDO Purkersdorf",
-- verankert am bestehenden Abschnitt.
INSERT INTO "DroneGroup" (id, name, "organizationId")
SELECT 'dronegroup-afkdo-purkersdorf', 'AFKDO Purkersdorf', id
FROM "Organization"
WHERE name = 'Abschnittsfeuerwehrkommando Purkersdorf';

-- Jedes bestehende Drohnengruppen-Mitglied, jedes bestehende Unterlagen-PDF und jede bestehende
-- Drohne gehören ab jetzt zu dieser einen Gruppe.
UPDATE "DrohnengruppeMembership" SET "droneGroupId" = 'dronegroup-afkdo-purkersdorf' WHERE "droneGroupId" IS NULL;
UPDATE "DroneDocument" SET "droneGroupId" = 'dronegroup-afkdo-purkersdorf' WHERE "droneGroupId" IS NULL;
UPDATE "Drone" SET "droneGroupId" = 'dronegroup-afkdo-purkersdorf' WHERE "droneGroupId" IS NULL;
```

The literal ids (`'district-17'`, `'dronegroup-afkdo-purkersdorf'`) are plain, stable, human-readable
strings rather than a generated `cuid()` — the same pattern already used for `AppSettings.id = "singleton"`
in this codebase. Raw SQL migrations cannot call Prisma's `cuid()` generator, and there is no requirement
that every row's id look like one.

After adding these statements, the file should read: the 6 `INSERT`/`UPDATE` statements above, **then**
Prisma's auto-generated `ALTER TABLE ... SET NOT NULL` statements for `DrohnengruppeMembership`,
`DroneDocument`, `Drone`. Leave the auto-generated statements' exact wording untouched — only prepend the
backfill block.

- [ ] **Step 2: Add the Feuerwehren-import function**

Add this new function right after the `DIENSTGRADE` constant, before `async function main() {`:

```typescript
/**
 * Legt die 6 neuen Abschnitte (171-176) und alle 124 Feuerwehren/BTF aus der Excel-Quelldatei an.
 * Abschnitt 177 (Purkersdorf) existiert bereits (siehe main()) und wird hier übersprungen - seine 9
 * Feuerwehren werden trotzdem per nummer-Match aktualisiert (parentId ergänzt), nicht dupliziert. Die
 * Excel-Daten (AFK_NUMMER/AFK_NAME) haben keine eigene Abschnittskommando-nummer (nur Feuerwehren haben
 * eine) - die hier konstruierte nummer folgt der bereits an Purkersdorf sichtbaren Konvention
 * ({Abschnittsnummer}00, z. B. Purkersdorfs bestehende '17700'). Gibt eine Map von AFK_NUMMER ->
 * Organization.id zurück, die seedDrohnengruppen für die Abschnitts-Verankerung nutzt.
 */
async function seedAbschnitteUndFeuerwehren(purkersdorfOrgId: string): Promise<Map<string, string>> {
  const district = await prisma.district.findUniqueOrThrow({ where: { number: '17' } });

  const abschnittIdByNummer = new Map<string, string>([['177', purkersdorfOrgId]]);

  for (const { nummer, name } of NEUE_ABSCHNITTE) {
    const orgName = `Abschnittsfeuerwehrkommando ${name}`;
    const org = await prisma.organization.upsert({
      where: { name: orgName },
      update: { districtId: district.id },
      create: {
        name: orgName,
        shortName: `AFKDO ${name}`,
        nummer: `${nummer}00`,
        type: OrganizationType.ABSCHNITTSKOMMANDO,
        districtId: district.id,
      },
    });
    abschnittIdByNummer.set(nummer, org.id);
  }

  const rows = feuerwehrenData.rows as {
    AFK_NUMMER: string;
    FW_ART: string;
    FW_NAME: string;
    FW_NUMMER: string;
  }[];

  for (const row of rows) {
    const parentId = abschnittIdByNummer.get(row.AFK_NUMMER);
    if (!parentId) continue;
    const name = row.FW_ART === 'BTF' ? row.FW_NAME : `FF ${row.FW_NAME}`;
    await prisma.organization.upsert({
      where: { nummer: row.FW_NUMMER },
      update: { parentId },
      create: {
        name,
        shortName: row.FW_NAME,
        nummer: row.FW_NUMMER,
        type: OrganizationType.FEUERWEHR,
        parentId,
      },
    });
  }

  return abschnittIdByNummer;
}
```

- [ ] **Step 3: Add the Drohnengruppen-seeding function**

/** Legt die 3 neuen Drohnengruppen an (die 4. existiert bereits seit der Backfill-Migration). */
async function seedDrohnengruppen(abschnittIdByNummer: Map<string, string>): Promise<void> {
  for (const { name, abschnittNummer } of NEUE_DROHNENGRUPPEN) {
    const organizationId = abschnittIdByNummer.get(abschnittNummer);
    if (!organizationId) {
      throw new Error(`Abschnitt ${abschnittNummer} für Drohnengruppe "${name}" nicht gefunden.`);
    }
    await prisma.droneGroup.upsert({
      where: { name },
      update: { organizationId },
      create: { name, organizationId },
    });
  }
}

  if (file.type !== 'application/pdf' && !file.name.toLowerCase().endsWith('.pdf')) {
    return { error: 'Nur PDF-Dateien sind erlaubt.' };
  }
  if (file.size > MAX_DOCUMENT_SIZE_BYTES) {
    return { error: 'Die Datei ist zu groß (maximal 10 MB).' };
  }

  const data = Buffer.from(await file.arrayBuffer());
  await prisma.droneDocument.create({
    data: {
      title,
      filename: file.name,
      sizeBytes: file.size,
      data,
      uploadedById: user.id,
      droneGroupId,
    },
  });

  revalidatePath('/admin/drohnen');
  revalidatePath('/drohnen/unterlagen');
  return {};
}

export async function deleteDroneDocument(documentId: string): Promise<void> {
  const doc = await prisma.droneDocument.findUniqueOrThrow({ where: { id: documentId } });
  await requireDroneGroupAccess(doc.droneGroupId);

  await prisma.droneDocument.delete({ where: { id: documentId } });
  revalidatePath('/admin/drohnen');
  revalidatePath('/drohnen/unterlagen');
}

/** Nur gerendert, wenn mehr als eine Feuerwehr zur Auswahl steht (Site-Admin, Abschnittsadmin, oder ein
 * Admin mehrerer Feuerwehren) - navigiert per ?org=<id>, damit die Auswahl bookmarkbar/teilbar bleibt.

 * 1-2 Optionen bleibt abschnittName meist ungesetzt und die Liste sieht wie zuvor aus. */
export function OrgSelect({ organizations, selectedId }: { organizations: OrgOption[]; selectedId: string }) {
  const router = useRouter();

  const groups = new Map<string, OrgOption[]>();
  for (const org of organizations) {
    const key = org.abschnittName ?? '';
    if (!groups.has(key)) groups.set(key, []);
    groups.get(key)!.push(org);
  }
  // Nur gruppieren, wenn wenigstens ein Eintrag tatsächlich einen abschnittName mitgibt - ein
  // Feuerwehr-Admin mit 1-2 Optionen und keinem abschnittName sieht weiterhin die schlichte flache Liste.

  return (
    <select
      value={selectedId}
      onChange={(event) => router.push(`/admin/heimatfeuerwehr?org=${event.target.value}`)}
      className="w-fit rounded-md border border-line bg-surface px-3 py-1.5 text-sm text-ink"
    >
      {hasGroups
        ? [...groups.entries()].map(([abschnittName, orgs]) => (
            <optgroup key={abschnittName} label={abschnittName || 'Ohne Abschnitt'}>
              {orgs.map((org) => (
                <option key={org.id} value={org.id}>

          ))
